# GUI viewers — architecture and design rationale

`guliwerr/gui/` — seventeen `handle` classes that turn an already-computed `Calc.*` result into an interactive `uifigure`: six Layered/HS classes (`AngSweepViewerGUI`, `SingleAngleViewerGUI`, `ModalShapeViewerGUI`, `DispersionViewerGUI`, `CombinedViewerGUI`, `DoubleSweepViewerGUI`), one Plate sibling for each (`AngSweepViewerGUIPlate`, `SingleAngleViewerGUIPlate`, `ModalShapeViewerGUIPlate`, `DispersionViewerGUIPlate`, `CombinedViewerGUIPlate`, `DoubleSweepViewerGUIPlate` — see "The Plate viewer family" below), and five isoFreq Layered siblings (`IsofreqSingleLayeredViewerGUI`, `IsofreqAngSweepViewerGUI`, `IsofreqModalShapeViewerGUI`, `IsofreqCombinedViewerGUI`, `FreqAngSweep2LayeredViewerGUI` — see "The isoFreq viewer family" below). All seventeen are launched through the `@Gui/` static-method namespace (`Gui.angSweepViewer`/`Gui.angSweepViewerPlate`/`Gui.isofreqAngSweepViewer`, `Gui.modalShapeViewer`/`Gui.modalShapeViewerPlate`/`Gui.isofreqModalShapeViewer`, etc.) the same way `Vis.plotXxx` fronts the plotting functions. `Gui.viewResult` / `Gui.viewSaved` pick the viewer for a result. The launcher pattern and `StructureControlGUI` (the entry point that builds a `Structure`, runs a calculation, and hands the result to a viewer) are in `docs/reference/architecture/gui.md` — not repeated here.

Every viewer is constructed invisible (`Visible='off'`) and exposes a `show()` method — the standing convention across this GUI layer (`StructureControlGUI` included) so a viewer can be built, driven through its callbacks, and inspected without ever painting a window. A constructor's errors carry `<Class>:constructor:<condition>` (e.g. `AngSweepViewerGUI:constructor:notCalculated`; the shared `GuiCommon` argument validators build the same form from the caller's class name).

## How the seventeen relate

| Class | Drives | Axis shape | Role |
|---|---|---|---|
| `AngSweepViewerGUI` | `CalcAngSweepHS` / `CalcAngSweepLayered` | 2D map (angle × velocity, colour as a 3rd dimension for two of its three graph types) | Standalone or embedded "bottom window" |
| `AngSweepViewerGUIPlate` | `CalcAngSweepPlate` | 2D map (angle × velocity, colour = mode type or confidence) | Standalone or embedded "bottom window" |
| `SingleAngleViewerGUI` | `CalcSingleHS` / `CalcSingleLayered` | 1D curve (velocity × value) | Standalone, or `AngSweepViewerGUI`'s own single-angle drill-down |
| `SingleAngleViewerGUIPlate` | `CalcSinglePlate` | 1D curve (velocity × mode type or confidence) | Standalone, or `AngSweepViewerGUIPlate`'s own single-angle drill-down |
| `ModalShapeViewerGUI` | `CalcAngSweepHS` / `CalcAngSweepLayered` / `CalcSingleHS` / `CalcSingleLayered` | depth-resolved field, `{3 × nLay}` panel grid | Standalone or embedded "top window" |
| `ModalShapeViewerGUIPlate` | `CalcAngSweepPlate` / `CalcSinglePlate` | depth-resolved field, `{3 × nLay}` panel grid | Standalone or embedded "top window" |
| `DispersionViewerGUI` | `CalcWavevecAngSweep2Layered` (one fixed angle — `angleIdx`, default 1, since `sweepResult` can carry more than one) | modal-shape grid + 1D dispersion curve, together | Standalone, or embedded (`parentContainer`) — the mechanism `DoubleSweepViewerGUI` uses |
| `DispersionViewerGUIPlate` | `CalcWavevecAngSweep2Plate` | modal-shape grid + 1D dispersion curve, together | Standalone, or embedded (`parentContainer`) — the mechanism `DoubleSweepViewerGUIPlate` uses |
| `CombinedViewerGUI` | any of the first three Layered rows (dispatches on class) | — | Composite host: wires a `ModalShapeViewerGUI` to whichever of `AngSweepViewerGUI`/`SingleAngleViewerGUI` fits the result |
| `CombinedViewerGUIPlate` | `CalcAngSweepPlate` / `CalcSinglePlate` (dispatches on class) | — | Composite host: wires a `ModalShapeViewerGUIPlate` to whichever of `AngSweepViewerGUIPlate`/`SingleAngleViewerGUIPlate` fits the result |
| `DoubleSweepViewerGUI` | `CalcWavevecAngSweep2Layered` (`numel(angles)>1` AND `numel(wavelengths)>1` — a genuine double sweep) | switches between `AngSweepViewerGUI`'s 2D map (at a chosen wavelength) and `DispersionViewerGUI`'s 1D curve (at a chosen angle) | Composite host, one level up from `CombinedViewerGUI` — see its own section below |
| `DoubleSweepViewerGUIPlate` | `CalcWavevecAngSweep2Plate` (`numel(angles)>1` AND `numel(wavVecs)>1` — a genuine double sweep) | switches between `AngSweepViewerGUIPlate`'s 2D map (at a chosen wavevector) and `DispersionViewerGUIPlate`'s 1D curve (at a chosen angle) | Composite host, one level up from `CombinedViewerGUIPlate` |
| `IsofreqSingleLayeredViewerGUI` | `CalcIsofreqSingleLayered` | 1D curve (kParRange × `\|G₃₃\|`) | Standalone, or `IsofreqAngSweepViewerGUI`'s own single-angle drill-down |
| `IsofreqAngSweepViewerGUI` | `CalcIsofreqAngSweepLayered` | 2D map (angle × kParRange, colour = `\|G₃₃\|`) | Standalone or embedded "bottom window" |
| `IsofreqModalShapeViewerGUI` | `CalcIsofreqAngSweepLayered` / `CalcIsofreqSingleLayered` | on-demand Green's-response field, `{3 × 1}` panel row (always exactly one "layer") | Standalone or embedded "top window" |
| `IsofreqCombinedViewerGUI` | `CalcIsofreqAngSweepLayered` / `CalcIsofreqSingleLayered` (dispatches on class) | — | Composite host: wires `IsofreqModalShapeViewerGUI` to whichever of `IsofreqAngSweepViewerGUI`/`IsofreqSingleLayeredViewerGUI` fits the result |
| `FreqAngSweep2LayeredViewerGUI` | `CalcFreqAngSweep2Layered` | rebuilds `IsofreqModalShapeViewerGUI`+`IsofreqAngSweepViewerGUI` against a different omega0 slice on every step | Composite host, but does *not* wrap `IsofreqCombinedViewerGUI` (see its own section below) |

Every Plate row is a deliberately separate class from its Layered counterpart, not a `class(sweepResult)` dispatch branch inside it — why, and what differs, is in "The Plate viewer family" below.

`AngSweepViewerGUI` and `SingleAngleViewerGUI` are a deliberate map/curve pair covering the same conceptual "bottom window" role for a sweep result vs. a single-angle result — `CalcSingleHS`/`CalcSingleLayered` have no angle axis to sweep, so a 2D map makes no sense for them, and `SingleAngleViewerGUI` is their axis-reduced analogue: same graph-type selector (`Classification curve`/`Ritz-mode curve`/`Green's-function curve`/`Ritz spectrum curve` vs. the map class's `Classification diagnostic`/`Ritz-mode map`/`Green's-function map`/`Ritz spectrum map`, the classification view first and the default), same classification bar, same click-to-select/crosshair mechanics, same status-line error handling, minus the angle dimension throughout. Concretely, both classes are driven by the `plotXxxMap`/`plotXxxDiagnostic` vs. `plotXxxCurve` split documented in `docs/reference/architecture/visual.md` — `SingleAngleViewerGUI` reuses `Vis.plotClassificationCurve`/`Vis.plotRitzModeCurve`/`Vis.plotGreenCurve`/`Vis.plotRitzSpectrumCurve` exactly as `AngSweepViewerGUI` reuses their map counterparts, rather than either GUI class re-deriving a 1D projection of the other's data itself.

**The Ritz-mode criterion.** The `'Ritz-mode curve'`/`'Ritz-mode map'` graph type shows a `criterionDropdown`, built by `GuiCommon.ritzCriterionDropdown` for both classes: `Ritz score` / `freqDisp` / `depthInsensitivity` (`ItemsData` `'ritzScore'` / `'freqDisp'` / `'depthInsensitivity'`, the `Vis` criterion names; `Ritz score` is the default). What each criterion shows, including the marked `freqDisp` veto level `RitzScore.MIN_FREQDISP`, is in `visual.md`, "Ritz-mode criteria"; the user's view of them is in `guiGuide.md` (Step 4, "Criterion"). On a layered result the `freqDisp` item is greyed (an italic grey `uistyle` — `uidropdown` has no per-item `Enable`) but still selectable, and the status line then says why it is not used (`GuiCommon.ritzCriterionNote`). The click readout adds the criterion value (`GuiCommon.selectionExtras`).

**The Ritz spectrum graph type.** `'Ritz spectrum curve'`/`'Ritz spectrum map'` (`Vis.plotRitzSpectrumCurve`/`plotRitzSpectrumMap`: |S(v)| from the stored modal numerators, no solve — `visual.md`, "Ritz spectrum plots") is the Ritz-side response next to the Green's-function view, and available on both calculation modes; on a `'ritzOnly'` result it is also the default background of the classification diagnostic/curve (the `Vis` functions' own default, so the viewers need no branch for it). The curve viewer draws it with the Ritz candidates marked (`showCands = true`; the function's default is off, as for the map). `SingleAngleViewerGUI.valueAtVelocity` — the crosshair and overlay lookup — reads the plotted line itself (the nearest sample of the spectrum curve) instead of recomputing it; `AngSweepViewerGUI.onMapClicked` needs no such branch, as it snaps to the nearest Ritz mode by `(angle, velocity)` whatever is displayed.

`ModalShapeViewerGUI` is the odd one out dimensionally: it renders a depth-resolved displacement (or Green's-response) field, not a velocity map or curve, so it pairs with *either* bottom-window class depending on what `CombinedViewerGUI` is given — the composite's whole job is picking the right pairing.

`DispersionViewerGUI` is not built from the other four at all, because it solves a different problem: stepping its "wavelength" control changes *which* `ritzSolver` the modal shape is drawn from (`sweepResult.sweeps{iw}.cs{angleIdx}.ritzSolver`), not just which mode within a fixed one, so `ModalShapeViewerGUI`'s angle-oriented API is not a clean fit — it renders modal shapes directly via `Vis.plotModalShape`, driven by its own `(wavelength step, branch)` state. `DoubleSweepViewerGUI` (see its own section below) is a genuine composite built partly FROM this class (and `AngSweepViewerGUI`/`ModalShapeViewerGUI`), but `DispersionViewerGUI` itself stays exactly this self-contained pair regardless.

## The shared duck-typed viewer interface

`AngSweepViewerGUI` and `SingleAngleViewerGUI` implement the same small interface — `.fig`, `.show()`, the `OnModeSelected` and `OnClassificationChanged` callback properties, and a `showCrosshairAt(angle, vel)` method — precisely so `CombinedViewerGUI` (and `ModalShapeViewerGUI`, on the receiving end of `OnModeSelected`) can wire against either one without knowing which it's holding. `CombinedViewerGUI.buildBottomViewer` dispatches once, by `isa(sweepResult, 'CalcSingleHS') || isa(sweepResult, 'CalcSingleLayered')`, and every line after that switch is unmodified regardless of the outcome. `SingleAngleViewerGUI.showCrosshairAt` accepts an `angle` argument purely for signature symmetry — there being only one possible angle (`obj.singleResult.angle`), the argument itself is unused.

This is a different duck-typing axis from the one `docs/reference/architecture/visual.md` documents for `Vis`'s own plotting functions (there, several `Calc.*` result classes expose identically-named fields and get dispatched on via `isa()`/`isprop()` inside a single plotting function). Here, it is two whole GUI *classes* that present an identical external surface so a third class can treat them interchangeably — the mechanism (duck typing) is the same idea one layer up, not the same code.

## The classification bar and the refresh chain

> **Experimental.** Surface-wave classification is checked against the measured maps published in Grabec et al. 2024 and the UTGS paper (arXiv:2510.10696), and there is no general agreement on which spectral peaks count as surface waves in strongly anisotropic materials. Thresholds, scores and the interface may change.

`ClassificationBar` (`guliwerr/gui/ClassificationBar.m`) is a handle class but not a viewer: one row of controls that `SingleAngleViewerGUI`, `AngSweepViewerGUI`, and `DispersionViewerGUI` each build into the second row of their top bar. It is one class rather than three copies because the rules it applies — which methods a result offers, the standards' values, the stale check — must be the same in every viewer. What the methods and standards mean is in `forwardCalcs_modeClassification.md`; the bar only selects and applies them.

| Control | What it does |
|---|---|
| **Method** | `Green` / `Refined` / `Ritz` (`ItemsData` `'green'` / `'refined'` / `'ritz'`) |
| **Standard** | `high` / `low` / `custom`; `custom` enables a numeric field on the method's own score scale (the scale `'high'` is compared on) |
| dB label | the selected standard's value and its dB equivalent (20 × value), e.g. `high = 0.16 (3.2 dB)`; a `'low'` compared with a structure-relative score says so (`ClassificationBar.standardText`) |
| **Reclassify** | `classifyTarget.classify(method, threshold)`: re-thresholds the stored candidates, no recomputation (`Refined` solves its spot directions on first use) |
| status | the active method and standard, or the stale banner |

**Unavailable methods.** The methods a geometry offers come from `CalcCommon.classificationMethods` (the same list the Calc classes validate against and `StructureControlGUI` offers). `uidropdown` has no per-item `Enable`, so the bar uses two different treatments, chosen by *why* a method is unavailable: a method that does not exist for the geometry is left out of the list (`Refined` on a layered result, where no spot score exists), while a method that exists but needs a recompute (`Green` and `Refined` on a `'ritzOnly'` result, which need `calcMode = 'full'`) stays in the list, greyed (italic grey `uistyle`, `GuiCommon.greyDropdownItem`), and selecting it reverts to the previous method with the reason on the bar's status line. Keeping the second kind visible says that the method exists and what it would take; removing it would hide that. The method dropdown's tooltip lists every method's availability and, for `Refined`, that its first use solves the spot directions and where the cost is documented. What the user sees: `guiGuide.md`, "Choosing and rerunning the classification".

**State and standards.** The bar reads everything from the result: `calcMode`, `activeMethod` / `activeThreshold`, and staleness. A result that stores no active method shows its `sawClassMethod` (if unset, `calcMode`'s own) and that method's default standard (`CalcCommon.defaultThreshold`) as a starting point, next to the stale banner. The standards' values come from `Vis.classificationScoreScale`, which reads the scoring classes' constants, so the bar and the plots' marker sizes cannot drift apart. Changing the method resets the standard to that method's default and the custom value to its `'high'` value, since the scales differ between methods (`docs/pitfalls.md`, "Numeric thresholds are per method").

**Stale results.** A result classified by another rule set (`CalcCommon.isStale`, the classification stamp) shows a stale banner on the status line and disables Reclassify (`guiGuide.md`); `classify` would refuse it anyway, and the rest of the viewer works as usual.

**`classifyTarget`.** The bar reads its state from `result` and calls `classify` on `classifyTarget`, by default the same object; both are fixed at construction (`ClassificationBar(parent, result, rowNo, classifyTarget)`). `DispersionViewerGUI` passes one wavelength slice (`sweeps{1}`) as `result` and the whole `CalcWavevecAngSweep2Layered` as `classifyTarget`, so a Reclassify there reclassifies every wavelength and reassembles the 2D maps; `DoubleSweepViewerGUI` builds its angular-mode `AngSweepViewerGUI` with the double sweep as `classifyTarget` (the viewer's third constructor argument, handed on to its bar) for the same reason. A slice is never reclassified on its own, which would leave the other wavelengths out of step.

**Refresh chain.** After a successful Reclassify the bar refreshes itself and calls the handler its owner set with `setReclassifyHandler`; each owner passes the refresh on, so every open view of the result shows the new classification:

1. `AngSweepViewerGUI` redraws the map with its axis-range fields and crosshair kept (`redrawClassified`; a plain `onGraphTypeChanged` would re-default the colour range and drop the crosshair), or, while drilled in, the nested single-angle curve (`SingleAngleViewerGUI.refreshClassification`). The drill-down's `SingleAngleViewerGUI` is built without a bar of its own (third constructor argument `false`, its bar row collapsed to height 0): the sweep's bar classifies every angle at once.
2. It then fires `OnClassificationChanged`. `CombinedViewerGUI` and `DoubleSweepViewerGUI` (angular mode) wire that to `ModalShapeViewerGUI.refreshClassification`, which rebuilds the SAW / limiting panel of the current angle; a standalone `SingleAngleViewerGUI` fires the same callback after its own Reclassify.
3. `DispersionViewerGUI.refreshClassification` redraws the branches (`Vis.plotDispersionCurves` reads `significantModesMap` live to highlight the classified ones) with the axis ranges kept, and the info panel's type line. The tracked branches themselves do not depend on the classification.

The chain works because nothing downstream keeps a copy of the classification: every viewer reads it through the result handles at draw time (`ModalShapeViewerGUI` below).

## AngSweepViewerGUI and the single-angle drill-down

`AngSweepViewerGUI`'s "View single angle" button swaps its map for an embedded `SingleAngleViewerGUI` built directly from `sweepResult.cs{angNo}` — the per-angle `CalcSingleHS`/`CalcSingleLayered` building block the sweep itself is already made of. This needs no recomputation: an angular sweep's constructor already populates `.cs` with one fully `calcAll()`'d single-angle result per angle, so drilling down is just handing an already-finished object to a new viewer, not running anything new. The map's own `graphTypeDropdown`/`criterionDropdown` stay the one set of controls while drilled in: the nested viewer is built with `hostControls = true` (its own two dropdowns hidden), and each graph type drives the curve at the same position in the two lists (`syncDrilledInView` → `SingleAngleViewerGUI.setView`; the `Items` lists are kept in the same order for this — classification, Green's function, Ritz mode, Ritz spectrum), so the choice carries over in both directions. The nested `SingleAngleViewerGUI`'s own `OnModeSelected` is forwarded through the outer object's `OnModeSelected` (`dispatchModeSelected`) — so a caller that wired `AngSweepViewerGUI` once (typically `CombinedViewerGUI`'s automatic linking) keeps working transparently whether the map or the drilled-down curve is currently showing.

`showCrosshairAt` follows the same forwarding logic in reverse, but does not require an exact angle match to do it: while drilled in, it finds the nearest angle by `min(abs(sweepResult.angles - angleVal))` — same nearest-match pattern `onMapClicked` already used — and, if that nearest angle differs from the one currently drilled into (e.g. because a linked `ModalShapeViewerGUI`'s own angle stepper moved on while this view stayed drilled in), calls `drillDownToAngle` to re-drill to the new angle *before* forwarding the crosshair request — without this, the single-angle curve could be left showing a stale angle with no indication anything had changed.

**Type filters, classification overlay and saved axis ranges.** The "Show types:" checkbox panel applies to every graph type. On the Classification diagnostic/curve it filters that plot's own per-type scatter series (one handle per type actually present, `DisplayName`=type name, from the default `colorBy='type'`), all on by default. On the Ritz-mode, Green's-function and Ritz spectrum map/curve, the same classified points are drawn on top by calling `plotClassificationDiagnostic`/`plotClassificationCurve` with `showGreenBackground=false`, then restyled by `GuiCommon.styleClassificationOverlay`: hollow rings in the type colour (so the Ritz shading or the heatmap stays readable inside them), sized by score as in the plots themselves (`visual.md`, "Classification plots"), non-pickable (clicks reach the underlying plot), with no legend, no limiting-velocity line, and the underlying plot's labels restored. Since every overlay ring is open, `'weak'` entries (open markers in the plots) are drawn as faint rings instead (edge alpha `GuiCommon.OVERLAY_WEAK_ALPHA`, read from the handles' `UserData.isWeak`). The overlay is off by default, so those plots open unchanged. On the 1D curves each overlay point is moved onto the *displayed* curve at its velocity (`SingleAngleViewerGUI.valueAtVelocity`, the crosshair's own lookup, which reads the plotted line), since `plotClassificationCurve` projects onto its own background curve. The checkbox list of either context is built by `GuiCommon.classificationTypeCheckboxes`, shared by both viewers. The diagnostic and the overlay each keep their own per-type state (`diagnosticTypeVisible`/`overlayTypeVisible`) across graph-type switches, via `rebuildTypeCheckboxes`'s `visState`/`onToggle` arguments. Each checkbox row has a colour swatch because the overlay has no legend. Each checkbox toggles its own series' `Visible` directly — no redraw. Separately, the angle/velocity/colour axis-range fields are saved (`savedAxisRange`) immediately before drilling into a single angle and restored by `returnToSweepView` on the way back, rather than re-defaulted by `buildMapContent`/`onGraphTypeChanged`, so a custom range survives the round trip.

**Export figure and side panel.** The side panel has a fixed width (`GuiCommon.SIDE_PANEL_WIDTH`, 230 px), so a wider window widens the plot rather than the range fields. Its "Show types:" header row carries an **[Export figure]** button (`GuiCommon.typesHeaderRow`; the checkbox list is then built without its own header, `rebuildTypeCheckboxes(..., showHeader=false)`). `GuiCommon.exportAxes` copies the plot into an ordinary figure: every object (`allchild`, so lines drawn with `HandleVisibility='off'` come too, hidden types stay hidden), the scales, colours, colormap, labels, legend, and colour bar, and the limits only where they are manual (a uiaxes not yet rendered can report the previous plot's auto limits). Before each draw `GuiCommon.clearAxes` clears what `cla` leaves: hidden-handle objects (such as the freqDisp veto line) and a label's `Interpreter='none'` (set on the Ritz-mode criterion label, which would otherwise leave the next TeX label printed raw).

**Top bar and selection readout.** The top bar has two rows: graph type, criterion, and the drill-down / crosshair controls on the first, the classification bar on the second. The criterion pair is visible only for the Ritz-mode graph type. A click's angle/mode #/velocity/type is kept in `selectionInfo`, followed by `GuiCommon.selectionExtras`' lines: for a classified mode the classification readout (`GuiCommon.classificationReadout`: method, score in dB, grade and supporting mode, e.g. `green score 12.4 dB (strong), supporting mode 3` — the supporting mode is the entry's own `modeNo`, the Ritz mode the classification attributes the wave to), then the shown criterion's value. Standalone, all of it is written to the status line (`GuiCommon.statusText`; `showSelectionInStatus`, default `isempty(parentContainer)`); embedded in `CombinedViewerGUI`/`DoubleSweepViewerGUI` only the classification and criterion lines are, because the modal-shape viewer above already shows the selection itself. `AngSweepViewerGUI`'s drill-down passes its own `showSelectionInStatus` to the nested `SingleAngleViewerGUI`.

**Green component and velocity range.** There is no Component dropdown: the Green's-function map/curve shows `|G13_eff|` (the ±k symmetrised component, the only one a result stores; `G13_− = G31_+` by reciprocity, so it comes from the angle's one +k solve, see `green.md`), and so do the classification diagnostic/curve backgrounds of a `'full'` result. `|G13_eff|` is the spectrum the Green existence scores read, so the classified points sit on the spectrum they were decided on. Any other component is a script call, e.g. `Vis.plotGreenMap(sweep, [], [], [], [], 'G33')`, which recomputes it for that call (`visual.md`). A `'ritzOnly'` result has no Green data: the Green's-function view reports `plotGreenMap`'s/`plotGreenCurve`'s error on the status line, and the classification view is drawn on the Ritz spectrum. The crosshair and overlay lookups on a curve read the curve shown. The velocity range defaults to the Green axis's end but starts at 0.9 × the slowest Ritz mode, since the axis itself starts at 0.3 km/s; without a Green axis (`'ritzOnly'`) both span the Ritz modes' velocities (the map over all angles).

The map's colour scale has a real constraint: its four graph types plot fundamentally different quantities on different natural scales (Green / Ritz spectrum map: log10-normalised `|G|` / `|S|`; Ritz-mode map: a criterion value; classification diagnostic: a categorical type or a score), so a single shared colour min/max control is only safe if it is *re-defaulted* from each graph type's own freshly-drawn `CLim` every time the type changes, rather than fixed once. `SingleAngleViewerGUI` sidesteps the issue entirely rather than solving a smaller version of it: none of its curve types use colour as a genuine data dimension by default (classification curve's `colorBy='type'` default uses fixed per-type swatches, not a continuous scale), so it only ever exposes two axis-range fields (velocity, value), not three.

## ModalShapeViewerGUI

`ModalShapeViewerGUI` renders a depth-resolved field — either a Ritz eigenvector's displacement or a Green's-response field at a chosen (angle, velocity, force direction) — into a `{3 × nLay}` grid of panels, one row per structure layer (substrate at the bottom, matching `Vis.plotModalShape`'s own layer-ordering convention) and one column per displacement/force component. It accepts either an angular-sweep result or a single-angle result directly: a `CalcSingleHS`/`CalcSingleLayered` input is packaged internally as a degenerate one-angle "sweep" (a plain struct exposing the same three fields — `.angles`, `.cs`, `.structure` — every read in the class actually uses, with `cs{1}` the result's own handle), since `CalcAngSweepHS`/`CalcAngSweepLayered`'s own `cs{iAngle}` element already has exactly that shape. No new rendering path is needed for the single-angle case; angle prev/next buttons degrade naturally to no-ops when `numel(angles)==1`.

**Live classification.** The classified modes are read through the result handles on every use (`significantModesAt(angNo)` = `cs{angNo}.classification.significantModes`), never copied at construction, so a Reclassify in a linked viewer's classification bar is seen here. `refreshClassification` rebuilds the SAW / limiting panel of the current angle and leaves the shown mode and shape as they are; `CombinedViewerGUI` and `DoubleSweepViewerGUI` call it from the bottom viewer's `OnClassificationChanged` (see "The classification bar and the refresh chain").

**windowMode and embedding.** Three ways to host the same rendering: `'combined'` (default) builds one `uifigure` with shapes on the left and controls on the right; `'split'` builds two independent figures — a `uifigure` control panel plus a classic `figure` for the shapes, because classic `axes()` cannot be parented inside a `uifigure` at all; and a fourth mode, embedding (`controlsParent`/`shapeParent` supplied), points the identical `'combined'`-style rendering at caller-owned `uigridlayout` regions of a shared figure instead of self-built ones — the mechanism `CombinedViewerGUI` uses to host this class's content inside its own window. Internally, `obj.embedded` is true whenever rendering goes through the pre-built `{3 × nLay}` `uiaxes` grid — both real embedding and standalone `'combined'` mode are the same code path, just pointed at different containers — and false only for standalone `'split'`, the one case still using a classic figure and `plotModalShape`'s/`plotGreenModalShape`'s own axes-array creation.

**Display: components or polarisation RGB.** A `Display` dropdown (`GuiCommon.shapeDisplayDropdown`, in every viewer that shows modal shapes; behaviour in `guiGuide.md`, Step 4) switches between the component panels and the polarisation-RGB panels (`dirs = 'rgb'`; the scheme is in `visual.md`). `GuiCommon.shapeAxesGrid` builds both axes sets once, in the same panel, and `GuiCommon.setShapeDisplayMode` shows one and clears the other.

That `uiaxes` grid (`GuiCommon.shapeAxesGrid`) is built from manually positioned `uiaxes` inside a plain `uipanel`, not a `uigridlayout` — a real constraint, not a style preference: a `uigridlayout` with two or more children actively re-manages each child's `PositionConstraint` on every `drawnow`, which silently reverts any attempt to trim a `uiaxes`'s default label/tick margin and reintroduces a visible gap between adjacent layers regardless of `RowSpacing`. A plain `uipanel` has no such active layout manager, so `Position`/`InnerPosition` set once survive `cla()`/redraw/`drawnow` unchanged. Row heights come from `Vis.calcModalShapeRowHeights` (see `docs/reference/architecture/visual.md`) — the same "boosted" weighting `redrawShape`'s own `Vis.plotModalShape(..., 'boosted', ...)` call uses — and must already match what `redrawShape` will actually render with, because the grid is fixed once at construction rather than rebuilt every redraw the way a classic figure's `Position` would be.

**Source toggle: Ritz modal shape vs. Green's response.** The two sources share the same `{3 × nLay}` rendering target but differ in what drives the "Mode:" field. In Ritz mode it is a discrete mode index (`currentModeNo`); in Green's-response mode it is re-purposed, with a relabelled meaning rather than a new widget, as a direct continuous velocity entry (`currentVel`) — there is no discrete mode to snap to for an arbitrary Green's-function velocity. `currentModeNo` is still kept pointed at the nearest Ritz mode throughout Green's-response mode, purely so a later switch back to Ritz modal shape starts somewhere sensible; it is never used to drive the Green's-response calculation itself. The Green's-response field fills the same grid as the Ritz shape: `Vis.plotGreenModalShapeLayered` for a layered structure (one row per layer, `'boosted'` row heights), `Vis.plotGreenModalShape` into the single row of a half-space.

**Angle stepping follows the physical wave, not the raw mode index — when the source is Ritz modal shape.** Ritz mode ordering by velocity can shuffle as a function of angle, so keeping the same raw index across an angle step can jump to the wrong branch entirely. `followPhysicalWave` re-anchors on the mode's current classification (`'SAW'`/`'limiting'`/`'none'`, itself overridable per-angle — see below) and looks for the same category at the new angle, closest by velocity for the `'limiting'` case. When the source is Green's response instead, there is no discrete mode/type to follow for an arbitrary continuous velocity, so angle stepping simply keeps the same velocity — the natural analogue of "same wave" when there is no branch identity to track.

**Session-local classification overrides.** "Mark current mode as SAW" / "…as limiting" let the user manually correct the automatic classification when it picks the wrong branch at a given angle — a cheap QC escape hatch, not a full re-classification workflow. These overrides are stored only on the `ModalShapeViewerGUI` instance itself (`obj.overrides`), never written back into the result's classification (`SetAccess=protected` there by design; the classification bar's Reclassify is the supported way to change it), and are consulted first by `classifyCurrentMode`/`followPhysicalWave` before falling back to the automatic classification — session-local and lost when the viewer is closed, deliberately, since adding a public mutator on `ModeClassification`/`CalcAngSweepHS`/`CalcAngSweepLayered` for a persistent version is a separate, larger decision this class does not make.

**Retention-aware recompute-on-demand.** Under `retentionLevel~='full'`, `cs{angNo}.ritzSolver.eigVecs_con` may have been pruned to only the significant modes, or cleared entirely (`docs/reference/architecture/forwardCalcs.md`'s retention-level table) — without a recompute path, the viewer would be silently frozen on stale data whenever a requested mode's column had been pruned away (`redrawShape`'s own `try`/`catch` swallows the error; easiest to trigger via a `CombinedViewerGUI` map click into a mode the sweep never retained). `resolveDisplayRitz` closes this: it returns `cs.ritzSolver` unchanged when `retentionLevel=='full'`, and otherwise recomputes a fresh, full-eigenvector `RitzSolverSAW` for that angle on demand (`RitzSolverSAW(cs.structure, 0)` — angle `0` because `cs.structure` is already rotated, same rule as `forwardCalcs.md`'s "Rotation convention: pass 0 to solvers after construction"), cached per angle in `obj.fullRitzCache` so repeated mode-stepping at the same angle doesn't re-solve on every redraw. The recomputed solver is never written back into `obj.sweepResult` — doing so would defeat `retentionLevel`'s RAM-saving purpose — so it lives only in this viewer's cache, lost when the viewer closes. A "does `eigVecs_con` have enough columns for `modeNo`" check is not a safe alternative: `RitzSolver.pruneEigVecs` *compacts* `eigVecs_con` down to `numel(keepCols)` columns rather than zero-filling the dropped ones, so column `j` of a pruned matrix is original mode `keepCols(j)`, not mode `j` — a column-count check that happened to pass would silently plot the *wrong* physical mode. Recompute is therefore unconditional under any non-`'full'` retention level, never gated on a column-count heuristic.

**Bidirectional wiring.** Two standalone windows link manually: `AngSweepViewerGUI.OnModeSelected` feeds `ModalShapeViewerGUI.goToSelection` (which dispatches to `goToMode` or `goToVelocity` depending on *this* window's own current source — the map class deliberately stays unaware of which one that is), and `ModalShapeViewerGUI.OnSelectionChanged` feeds the map's `showCrosshairAt` in return. `CombinedViewerGUI` performs exactly this wiring automatically.

## CombinedViewerGUI

A composite that owns no rendering logic of its own — its entire job is (a) picking the right bottom-window class for the given result (`AngSweepViewerGUI` for an angular sweep, `SingleAngleViewerGUI` for a single-angle result, dispatched by `isa()`) and (b) wiring it to a `ModalShapeViewerGUI` bidirectionally, exactly as a caller would by hand for two standalone windows. Both underlying classes stay fully independent and unmodified in their own logic in every mode. The bottom viewer carries the classification bar; its `OnClassificationChanged` is wired to `ModalShapeViewerGUI.refreshClassification`, so a Reclassify updates both halves.

`windowMode` controls only how many physical windows the composite opens, not what it computes or wires: `'combined'` (default) is one `uifigure` with the modal-shape half on top (shapes left, controls right) and the bottom viewer below, separated by a thin visible divider panel; `'split'` is two independent windows (`ModalShapeViewerGUI` standalone in its own default `'combined'` mode, plus the bottom viewer standalone); `'fullSplit'` is three windows, splitting `ModalShapeViewerGUI` itself further into its own controls-only and shapes-only figures. `obj.fig` is only ever populated for `'combined'` — there is no single shared figure in the other two modes, so it is left `[]` there, and callers should use `show()` (which delegates to each sub-viewer's own `show()`, correct regardless of how many figures it owns) rather than touching `obj.fig` directly.

`CombinedViewerGUIPlate` is the line-for-line Plate sibling — same `windowMode` mechanics, same bidirectional wiring, dispatching its bottom half on `isa(sweepResult, 'CalcSinglePlate')` instead of `CalcSingleHS`/`CalcSingleLayered` — wiring `ModalShapeViewerGUIPlate` to whichever of `AngSweepViewerGUIPlate`/`SingleAngleViewerGUIPlate` fits (see "The Plate viewer family" below).

## DispersionViewerGUI

Covers `CalcWavevecAngSweep2Layered` at one fixed angle — a wavevector/wavelength sweep, not the angular sweep the other four classes are built around. It is layered-only (`CalcWavevecAngSweep2Layered` has no half-space equivalent) and offers no Green's-response toggle and no SAW/limiting override panel — both omissions match the physical scope of the underlying result class, not an oversight.

Unlike `CombinedViewerGUI`, this is one class building both halves itself, for the reason given under "How the seventeen relate". Branch continuity across wavelength steps is handled upstream, by `DispersionBranches.track` (`branchModeNoMap`, an `[nWav × nCompModes]` array built once at construction) — stepping a branch index at the GUI layer is then just incrementing a column index, with no "follow the physical wave" re-derivation needed the way `ModalShapeViewerGUI`'s angle-stepping requires. `DispersionBranches.track` itself requires `retentionLevel='full'` on the sweep (the only retention level that keeps every Ritz eigenvector column, needed because a branch can drift through classification wobble between wavelength steps) — checked by `DispersionViewerGUI`'s constructor before anything else needing `calc()` to have happened.

**Classification bar.** The map side carries a classification bar above the dispersion curves (`Green` / `Ritz`, the layered methods), wired as described in "The classification bar and the refresh chain" above: a Reclassify reclassifies every wavelength of the whole `CalcWavevecAngSweep2Layered`, and `refreshClassification` redraws the branches (`Vis.plotDispersionCurves` highlights the classified ones, read live from `significantModesMap`). Branch tracking does not depend on the classification.

**`sweepResult` can carry more than one angle, and embedding.** `angleIdx` (3rd constructor argument, default 1) is a bounds check, not a hard restriction: `sweepResult` can be a genuine multi-angle `CalcWavevecAngSweep2Layered`, and `angleIdx` just picks which one this particular view is fixed at (still always a *single* fixed-angle view — `angleIdx` adds no angle stepper here). Every internal read uses `.cs{angleIdx}`/`significantModesMap{angleIdx}`, and `Vis.plotDispersionCurves`/`DispersionBranches.track` take the same `angleIdx` parameter so the whole chain stays consistent. Separately, a 4th constructor argument (`parentContainer`) lets this class build inside a caller-owned `uigridlayout` region instead of a fresh `uifigure` — the same single-argument convention `AngSweepViewerGUI` already uses (not `ModalShapeViewerGUI`'s two-argument `controlsParent`/`shapeParent` one, since this class is already a self-contained composite the way `ModalShapeViewerGUI` alone is not). `windowMode` must be `'combined'` (or omitted) when `parentContainer` is given — `'split'`+`parentContainer` errors (`DispersionViewerGUI:constructor:splitRequiresStandalone`, mirroring `ModalShapeViewerGUI`'s identical restriction). Both exist so that `DoubleSweepViewerGUI` (see its own section below) can re-embed a fresh `DispersionViewerGUI` at a caller-chosen angle, inside its own window, every time its dispersion mode is (re)built.

`windowMode` (`'combined'`/`'split'`) works exactly as it does for `ModalShapeViewerGUI`/`CombinedViewerGUI` — one shared figure vs. a modal-shape figure plus a separate map figure. Six curve types are offered (`'wavelength-freq'` (default), `'wavelength-vphase'`, `'k-freq'`, `'k-vphase'`, `'freq-vphase'`, `'freq-vgroup'`; `k = 2π/wavelength`), rendered by the dedicated `Vis.plotDispersionCurves` rather than a new branch inside `plotDispersionMap` — the two already-existing "map" classes cover genuinely different data shapes (a multi-angle 2D scatter vs. a fixed-angle 1D curve set), and a fixed-angle case forced into `plotDispersionMap`'s own rendering would just be a degenerate single column. Because the X/Y meaning genuinely changes with curve type (wavelength, wavenumber, frequency, or velocity on either axis), both the axis-range field *labels* and their default values are refreshed on every redraw (`redrawMap`), unlike `AngSweepViewerGUI`'s side panel, where angle/velocity never change meaning.

**Green's-function background.** `sweeps{iw}` (each a full `CalcAngSweepLayered` at that wavelength step) already carries its own Green angle × velocity map under `calcMode='full'`. Without drawing it, the tracked branch lines are the only thing shown, with no indication of which branch actually rides a genuine Green's-function peak vs. which is a weaker/background Ritz mode. `showGreenBgCheckbox` toggles a `pcolor` heatmap drawn behind the lines, built by `Vis.plotDispersionCurves`'s own private `plotWavevecGreenBackground` helper from each step's `|G13_eff|` column (`greenAbsG13EffMap`). The steps' `greenVelAxis` normally coincide (the substrate limiting velocities and `vMax` do not change with wavelength), but nothing guarantees it, so the per-wavelength columns are `interp1`'d onto one shared velocity axis before `pcolor` — any out-of-range cell interpolates to `NaN`, which `pcolor` leaves blank.

Only 2 of the 6 curve types (`'wavelength-vphase'`, `'k-vphase'` — the ones with a velocity y-axis) can show this background: the 4 frequency-based types would need a non-rectangular background grid (`freq = vel/wavelength` rescales differently per wavelength column), which is not implemented — `Vis.plotDispersionCurves` errors clearly (`Vis:plotDispersionCurves:backgroundNeedsVphase`) if asked for the background on an unsupported curve type. `DispersionViewerGUI` never lets a user hit that error: `obj.hasGreenData` (computed once at construction from `sweeps{1}.greenVelAxis` being non-empty) and curve-type membership together gate `showGreenBgCheckbox.Enable` (`onCurveTypeChanged`, which fires on both the dropdown's and the checkbox's `ValueChangedFcn`), and `redrawMap` independently recomputes the same gate before calling `Vis.plotDispersionCurves` — deliberately not trusting `Enable`, since `buildMapPanel`'s first `redrawMap()` call runs before `onCurveTypeChanged` has synced it.

Unlike `plotClassificationDiagnostic`'s own `showGreenBackground` (default `true`, warns and skips silently if data happens to be missing), `Vis.plotDispersionCurves`'s default is `false` and it *errors* rather than warns when requested without full-mode data — deliberately different defaults for a direct API caller: getting Green data here means paying for `calcMode='full'` on the whole wavelength sweep, a real cost this function's caller has not necessarily opted into, so silently defaulting to drawing it (with a warning on the common ritzOnly case) would be the wrong default here even though it's the right one for `plotClassificationDiagnostic`'s single-sweep case.

**Show Ritz branches.** Paired with the Green background toggle above — `Vis.plotDispersionCurves` takes a `showRitzBranches` parameter (default `true`) and `DispersionViewerGUI` a matching `showRitzBranchesCheckbox`, unconditionally enabled (branch lines need neither `calcMode='full'` nor a particular `curveType`, unlike the Green background, so there is no equivalent `Enable`-gating to do). Unlike the background, which genuinely adds or removes a `pcolor` object, unchecking this toggle does not skip plotting the lines or return empty placeholders: `plotDispersionCurves` still computes and returns the full `hLines` array, just with `Visible='off'` on each handle — the same "toggle an already-drawn handle" convention `AngSweepViewerGUI`'s per-type checkboxes use (see "Type filters, classification overlay and saved axis ranges" above). This keeps `XData`/`YData` (and therefore `DispersionViewerGUI.syncCrosshair`, which reads them directly) working regardless of visibility, and lets a caller flip a branch back on without a redraw. `onMapClicked`'s nearest-point search skips `Visible='off'` lines as well as non-`isgraphics` ones; otherwise a click near a hidden branch could silently snap the selection to a branch the user cannot see.

**`DispersionViewerGUIPlate` is a separate class, not a mode of this one** — part of the six-class Plate viewer family (see its own section below). Drives `CalcWavevecAngSweep2Plate` instead of `CalcWavevecAngSweep2Layered`, via `Vis.plotDispersionCurvesPlate` instead of `Vis.plotDispersionCurves` — copied structure (windowMode, embedding, shape grid, axis ranges, crosshair/click-to-select) but no Green controls at all, a colour-by-type/branch selector and Christoffel-bounds toggle in place of the Green/Ritz-branches checkboxes, and modal-shape frequency read from `RitzSolverLamb.freqsPhysical` directly rather than a re-derived `vel/wavelength`.

## DoubleSweepViewerGUI

Covers a genuine *double* sweep — `CalcWavevecAngSweep2Layered` with both `numel(angles)>1` and `numel(wavelengths)>1` — with a button that switches between an angular-map view (at a chosen fixed wavelength) and a dispersion-curve view (at a chosen fixed angle), each remembering its own axis-range settings across the switch.

**Why a new class, not a `CombinedViewerGUI` mode.** `CombinedViewerGUI` already has a conceptually similar "map ↔ single-angle curve" swap — but it lives entirely *inside* `AngSweepViewerGUI` itself (see "AngSweepViewerGUI and the single-angle drill-down" above): a stable content slot whose children get destroyed/rebuilt, an external toggle button that survives the swap, saved-and-restored axis-range fields, and event-forwarding so `CombinedViewerGUI`'s own one-time wiring never needs to know which sub-view is active. That swap works *bottom-only* because both sides of it pair naturally with the same top (`ModalShapeViewerGUI`, angle-oriented). Angular-map mode and dispersion-curve mode don't share that: `DispersionViewerGUI`'s whole reason for existing as a separate class is that `ModalShapeViewerGUI`'s angle-oriented API doesn't fit wavelength-stepping, so it renders modal shapes itself instead (see its own section above). `DoubleSweepViewerGUI` therefore swaps a whole top-and-bottom *pair* at once — `ModalShapeViewerGUI`+`AngSweepViewerGUI` (angular mode) versus `DispersionViewerGUI`'s own self-contained shape+curve content (dispersion mode) — following the *exact same mechanical pattern* as `AngSweepViewerGUI`'s own swap (stable `contentParent` slot, external toggle button, saved-and-restored axis ranges), just one level up and swapping two objects instead of one.

**Angular mode** is `ModalShapeViewerGUI`+`AngSweepViewerGUI`, wired exactly as `CombinedViewerGUI` wires them, pointed at `sweepResult.sweeps{currentWavNo}` — already a complete, independently-`calc()`'d `CalcAngSweepLayered` (the double sweep's own per-wavelength building block), so switching wavelength needs no recomputation, just rebuilding these two viewers against a different element of `sweepResult.sweeps`.

**Dispersion mode** is `DispersionViewerGUI`, embedded via its `parentContainer` argument and pointed at `sweepResult` directly with `angleIdx=currentAngNo` — again no recomputation, just re-embedding at a different angle slice.

**`currentWavNo`/`currentAngNo` are tracked independently and persist across mode switches** — entering angular mode always uses whatever wavelength was last active (from a previous visit, or from wherever the dispersion view's own wavelength stepper was left when the user switched away from it), and entering dispersion mode always uses whatever angle was last active (from a previous visit, a map click in angular mode, OR `ModalShapeViewerGUI`'s own angle-stepping there). Both `AngSweepViewerGUI.OnModeSelected` and `ModalShapeViewerGUI.OnSelectionChanged` are wrapped (`onAngularModeSelected`/`onAngularSelectionChanged`) to update `currentAngNo` in addition to the bidirectional map↔shape wiring `CombinedViewerGUI` itself already performs — angle *selection* happens the same two ways it always did, this class just also listens in.

**Reclassify classifies the whole double sweep.** Both modes carry a classification bar, and both classify the whole `CalcWavevecAngSweep2Layered` (the angular sweep viewer is built with `classifyTarget = sweepResult`). In angular mode a Reclassify redraws the sweep viewer and refreshes the modal-shape viewer (the `CombinedViewerGUI` chain); in dispersion mode the dispersion viewer redraws its own branches. A mode switch rebuilds the other side from the live result, so it shows the new classification too.

**RAM warning, deliberately not hidden.** Dispersion mode needs `sweepResult` `calc()`'d with `retentionLevel='full'` (`DispersionBranches.track`'s own requirement) — not validated at construction, since angular mode alone doesn't need it, and requiring it unconditionally would block viewing a large double sweep computed more cheaply purely for its angular side. Switching to dispersion mode on a `sweepResult` that wasn't computed with `retentionLevel='full'` surfaces `DispersionBranches.track`'s own `DispersionBranches:track:missingEigVecs` error instead, exactly as constructing a standalone `DispersionViewerGUI` already does. Full retention across both swept axes of a real-sized double sweep is a genuinely large RAM cost (`docs/pitfalls.md` NUM4: a nested sweep already multiplies eigenvector RAM across its outer loop under `'full'`) — this is a real constraint on how large a double sweep this viewer can practically be pointed at, not a hidden one.

Single window only — no `combined`/`split`/`fullSplit` toggle of the kind `CombinedViewerGUI`/`ModalShapeViewerGUI` offer. A deliberate scope decision: a second, independent axis of window-count variation on top of the mode switch was not built speculatively.

**Switching mode while drilled into `AngSweepViewerGUI`'s own single-angle view.** `AngSweepViewerGUI`'s "View single angle" drill-down (see its own section above) destroys `xMinField`/`yMinField`/`cMinField` — `delete(contentParent.Children)` in `drillDownToAngle`, with nothing resetting the now-dangling property references themselves. Reading `.Value` off those directly when leaving angular mode while drilled in throws "Invalid or deleted object" — a real, expected path, not an edge case. `onSwitchMode` guards against this by checking `AngSweepViewerGUI.isDrilledIn` (`SetAccess=private`, externally readable for exactly this) and calling `angularSweepViewer.returnToSweepView()` first when true — the same thing the user would get by clicking "\<\< Back to angular sweep" themselves. Nothing about *which angle* dispersion mode ends up at is lost by this: `DoubleSweepViewerGUI.currentAngNo` is this class' own state, already kept correct regardless of `AngSweepViewerGUI`'s drill state (updated on every map click and every modal-shape angle-step, per "currentWavNo/currentAngNo are tracked independently" above) — only the drilled-in single-angle curve's own axis range is not preserved across the switch, since neither of its axes correspond to the 2D map's angle/velocity meaning in the first place.

`DoubleSweepViewerGUIPlate` is the Plate sibling — identical mode-switch mechanics, `wavVecs` (Plate's own sweep axis) in place of `wavelengths` throughout, `ModalShapeViewerGUIPlate`+`AngSweepViewerGUIPlate` for angular mode and an embedded `DispersionViewerGUIPlate` for dispersion mode (see "The Plate viewer family" below). `StructureControlGUI` opens neither double-sweep viewer after Run; both are reached through `Gui.doubleSweepViewer`/`Gui.doubleSweepViewerPlate` directly, or automatically through `Gui.viewResult` / `Gui.viewSaved` for a genuine double sweep.

## The Plate viewer family

Six classes covering the free-plate forward-calc stack (`CalcSinglePlate` → `CalcAngSweepPlate` → `CalcWavevecAngSweep2Plate`, `docs/reference/architecture/plate.md`), one sibling per Layered viewer: `ModalShapeViewerGUIPlate` (top-half modal shapes), `SingleAngleViewerGUIPlate`/`AngSweepViewerGUIPlate` (bottom-half 1D curve / 2D map), `CombinedViewerGUIPlate` (the two combined), `DispersionViewerGUIPlate` (fixed-angle wavevector dispersion) and `DoubleSweepViewerGUIPlate` (angular-map ↔ dispersion-curve toggle for a genuine double sweep). This family is Ritz-only — no Green's-function solve anywhere in it (`plate.md`, "Why Plate is a separate, leaner class family") — and every class in it is a **deliberately separate class from its Layered counterpart, not a `class(sweepResult)` dispatch branch inside it**, the same "separate parallel sibling" convention used for every Plate addition since `CalcSinglePlate` itself. Two reasons hold throughout the family:

**No Green controls anywhere in this family — absent, not disabled.** No Green's-function analogue exists for a free plate, so every Plate viewer is missing a whole control surface (source toggle, force-direction dropdown, continuous-velocity jump-to, Green background rendering) *entirely*, rather than having it gated behind a disabled widget. The properties are not merely disabled: `isprop(gui, 'sourceDropdown')` and the like are false.

**Mode quality is mode-TYPE classification, not SAW classification.** Layered's `graphTypeDropdown` (classification / Ritz-mode / Green's-function / Ritz spectrum), its `criterionDropdown` (`Ritz score` / `freqDisp` / `depthInsensitivity`) and the classification bar have no Plate equivalent. Plate viewers instead expose exactly one graph type (there is nothing else to switch to), with a `criterionDropdown` of `'Mode type'`/`'Confidence'` (`RitzSolverLamb.modesType`/`modeTypeConfidence`, the same fields `classifyBranches`/`plotDispersionCurvesPlate` use — `plate.md`, "Mode-type classification"). This drives `Vis.plotRitzModeCurvePlate`/`Vis.plotRitzModeMapPlate`, the Plate-side analogues of `Vis.plotRitzModeCurve`/`Vis.plotRitzModeMap`: for `'modeType'`, colour is the same 4-colour categorical map `plotDispersionCurvesPlate` uses (a legend, not a colorbar, since a discrete classification has no continuous range); for `'confidence'`, colour/y-axis is the continuous `[0,1]` score, colorbar included, mirroring the original functions' own design.

**A few genuine simplifications versus the Layered originals**, each made because the underlying concept has no Plate equivalent to preserve:

- **`ModalShapeViewerGUIPlate` drops `followPhysicalWave`/`classifyCurrentMode` angle-stepping** (`ModalShapeViewerGUI`'s SAW/limiting-type-following logic, keyed to the classification's significant modes, which Plate doesn't have) in favour of the plain "keep the same raw mode index across an angle step" default — documented in the class's own docblock as a deliberate choice. If a mode's physical identity needs following across angle (mode order by velocity can shuffle for Plate exactly as it can for SAW), the user re-selects by type/confidence directly.
- **No per-type "Show types:" checkbox filter** in `SingleAngleViewerGUIPlate`/`AngSweepViewerGUIPlate`. `Vis.plotRitzModeCurvePlate`/`plotRitzModeMapPlate` return ONE scatter handle (colour via an RGB matrix), not one handle per type the way `plotClassificationCurve`/`plotClassificationDiagnostic` do, and splitting them into 4 series to support per-type toggling has not been done.
- **`AngSweepViewerGUIPlate`'s colour-range fields are enabled only for `criterion='confidence'`** — `'modeType'`'s categorical RGB colouring has no continuous range to control, so the fields are disabled (not hidden) rather than showing a meaningless `CLim`.

Everything else — `windowMode` (combined/split/fullSplit), embedding via `controlsParent`/`shapeParent`, the shape-axes grid (`Vis.plotModalShape` is already solver-agnostic, taking a `RitzSolverLamb` exactly as it takes a `RitzSolverSAW`), axis-range fields, crosshair/click-to-select, single-angle drill-down, `DoubleSweepViewerGUIPlate`'s mode-switch/axis-range-persistence mechanics — is mechanically identical to the Layered originals, copied rather than shared. The remaining per-class differences sit beside each Layered original above (`CombinedViewerGUIPlate`, `DispersionViewerGUIPlate`, `DoubleSweepViewerGUIPlate`).

**`StructureControlGUI` routing.** Plate Single/AngSweep route to `Gui.combinedViewerPlate` and Plate 2-axis to `Gui.dispersionViewerPlate`, mirroring the Layered isoWavevec branch exactly; `DoubleSweepViewerGUIPlate` is not opened by it (see its paragraph above). The control panel's own handling of Plate mode — which toggles it hides, what its three generic fields mean, and the `retentionLevel` dropdown gap — is in `docs/reference/architecture/gui.md`.

## The isoFreq viewer family

Five classes covering the isoFreq side of the Layered forward-calc stack (`CalcIsofreqSingleLayered` → `CalcIsofreqAngSweepLayered` → `CalcFreqAngSweep2Layered`, `docs/reference/architecture/forwardCalcs.md`'s "isoWavevec vs. isoFreq"). This family is Green's-function only — no Ritz solve anywhere in it — which shapes every one of its classes:

**No graph-type/criterion/source dropdown anywhere in this family.** `IsofreqSingleLayeredViewerGUI`/`IsofreqAngSweepViewerGUI` have exactly one possible graph (the Green `|G₃₃|` field vs. kParRange — no Ritz-mode/classification alternative exists to choose between), so the dropdown itself is dropped, not left disabled — the same "absent, not disabled" precedent the Plate family established for its own missing Green controls. `IsofreqModalShapeViewerGUI` drops `ModalShapeViewerGUI`'s `sourceDropdown` for the identical reason: Green's response is the *only* source (no Ritz side to toggle to), so `forceDirDropdown` is unconditionally visible instead of appearing only once a source toggle selects it.

**A renamed duck-typed interface: `OnPointSelected`/`showCrosshairAt`/`goToPoint`, keyed on `(angle, kParVal)`.** `AngSweepViewerGUI`'s own `OnModeSelected`/`showCrosshairAt`/`goToSelection` triple assumes a discrete Ritz mode index (`modeNo`) — kParRange has no such discrete structure here (`CalcIsofreqSingleLayered`'s own docblock calls it "the PHYSICALLY MEANINGFUL swept quantity", a continuous axis), so `IsofreqSingleLayeredViewerGUI`/`IsofreqAngSweepViewerGUI`/`IsofreqModalShapeViewerGUI` implement an honestly-renamed analogue instead of reusing a signature built for a different kind of selection. `IsofreqAngSweepViewerGUI`'s click handler is correspondingly simpler than `AngSweepViewerGUI.onMapClicked`: nearest-angle-then-nearest-kParRange-sample, no "nearest mode within that angle" second search, since there is no mode list to search.

**On-demand Green's-response displacement field.** `IsofreqModalShapeViewerGUI` uses the same mechanism as `ModalShapeViewerGUI`'s Green's-response source (`GreenSolver.calc` with `nargout>1`, then `Vis.plotGreenModalShapeLayered`, or `Vis.plotGreenModalShape` for a half-space), driven with `scanMode='isoFreq'` and the slice's own `omega0`, converting the continuous kParRange state to a velocity via `v = omega0/kParRange` — the same conversion `CalcIsofreqSingleLayered.calc()` performs before calling `GreenSolver.calc`. Two consequences:

- **Layered and half-space alike.** A layered structure (the usual isoFreq case) is drawn by `Vis.plotGreenModalShapeLayered` from `GreenSolver`'s layered full output (`k3OutLayered`/`polarizationULayered`/`partialAmplitudeLayered`/`hScaleOut`; `docs/reference/architecture/green.md`, "Depth-resolved field, layered structures"), one row per layer with the same `'boosted'` row heights as the Ritz shape; a half-space by `Vis.plotGreenModalShape` from the plain `.dispField`. `ModalShapeViewerGUI`'s Green's-response source does the same. No isoFreq-specific scaling is needed: `GreenSolver.calc` stores `hScaleOut = omega0/v = |k_parallel|`, so every depth is already in units of the selected wave's own wavelength (checked: the isoFreq field at `(omega0, kPar)` equals the isoWavevec field at `v = omega0/kPar` on the stack rescaled to `lambda/kPar`, to round-off). Solver errors are caught onto the status line by `redrawShape`'s try/catch.
- **Double-rotation avoidance across the two accepted input shapes.** `IsofreqModalShapeViewerGUI` accepts either `CalcIsofreqAngSweepLayered` directly or a `CalcIsofreqSingleLayered` adapted into a degenerate 1-angle struct (mirroring `ModalShapeViewerGUI`'s `CalcSingleHS`/`CalcSingleLayered` adapter), but this adapter tracks a `structureAlreadyRotated` flag and passes `angle=0` to `GreenSolver.calc` for the single-point case — the rule and the reason are in `docs/reference/architecture/forwardCalcs.md`, "Rotation convention: pass 0 to solvers after construction", which also says which of the two isofreq classes holds a rotated `.structure`. The field rendered from a single-point adapter is therefore numerically identical to the field from a genuine sweep at the same angle.

Angle stepping in `IsofreqModalShapeViewerGUI` keeps the SAME kParRange across the step — the direct analogue of `ModalShapeViewerGUI`'s own Green's-response angle-stepping ("no discrete mode/type to follow for an arbitrary continuous velocity — same velocity, different angle"), just with kParRange (the axis both the map and curve are actually built on) standing in for velocity. Its `<<`/`>>` buttons likewise mirror `ModalShapeViewerGUI`'s fixed `VEL_STEP`, but step one sample of the slice's own kParRange grid (`stepKPar`, clamped at the ends), and the row's trailing label shows `v = omega0/kParRange`.

**`IsofreqCombinedViewerGUI`** is a line-for-line mirror of `CombinedViewerGUI` (same `windowMode` combined/split/fullSplit, same bidirectional wiring, renamed callback names) — `buildBottomViewer` dispatches `isa(sweepResult, 'CalcIsofreqSingleLayered')` → `IsofreqSingleLayeredViewerGUI` else → `IsofreqAngSweepViewerGUI`, top always `IsofreqModalShapeViewerGUI`.

**`FreqAngSweep2LayeredViewerGUI` does *not* embed `IsofreqCombinedViewerGUI`.** Mirrors exactly why `DoubleSweepViewerGUI` doesn't embed `CombinedViewerGUI` either (see that class's own section above): the composite class has no `parentContainer` support, only its two children do. Instead, an omega0 stepper directly builds+wires `IsofreqModalShapeViewerGUI`+`IsofreqAngSweepViewerGUI` into its own layout on every step, pointed at `sweepResult.sweeps{currentOmegaNo}` — a direct copy of `DoubleSweepViewerGUI.buildAngularContent`/`onWavChanged`, substituting `sweeps{currentOmegaNo}` for `sweeps{currentWavNo}`. Unlike `DoubleSweepViewerGUI`, there is no second mode to switch to (no dispersion-curve/branch-tracking view exists for isoFreq — no Ritz, nothing to track), so every omega0 step simply rebuilds the same one view fresh, always resetting to the map (no drilled-in state carried across a step — the underlying `CalcIsofreqSingleLayered` object at a given angle is a genuinely different object at a different omega0, so there is no "same angle, new omega0" state worth preserving). Single window only, matching `DoubleSweepViewerGUI`'s own stated scope decision.

**`StructureControlGUI` routing.** isoFreq Single/AngSweep both route to `Gui.isofreqCombinedViewer` (as HS/isoWavevec Single/AngSweep route to `Gui.combinedViewer`, and Plate Single/AngSweep to `Gui.combinedViewerPlate`); isoFreq 2-axis routes to `Gui.freqAngSweep2LayeredViewer`. Every combination in `docs/reference/architecture/gui.md`'s routing table has a viewer.

## A recurring gotcha: `cla()` does not reset axis-limit modes

Both `AngSweepViewerGUI.onGraphTypeChanged` and `DispersionViewerGUI.redrawMap` explicitly reset `XLimMode`/`YLimMode` (and, for the map class, `CLimMode`) to `'auto'` immediately after `cla()`, because `cla()` clears an axes' *children* only, not its limit-mode state. If a previous draw called `xlim`/`ylim`/`clim` explicitly (as `plotGreenMap` does for `CLim`, or as either class's `applyAxisRange` does whenever the user has typed a range), MATLAB leaves the axes in `'manual'` limit mode, so a later redraw that sets no limits of its own (Ritz-mode map, classification diagnostic) would silently inherit the *previous* draw's stale range instead of auto-scaling to its new data. The colour-range control's "re-default the field from the freshly drawn `CLim`" mechanism depends on this reset too. Any viewer that redraws into a persistent `uiaxes`/axes object under user-controlled range fields needs the same explicit reset.
