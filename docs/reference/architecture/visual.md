# Vis — architecture and design rationale

`guliwerr/visual/@Vis/` (`Vis.plotXxx`/`Vis.calcXxx`, called directly — `Vis.plotModalShape(ritzSolver, modeNo)`). A namespace of 43 public static methods (one file each in `@Vis/`, all declared in `Vis.m`'s `methods (Static)` block — the authoritative list), plus 33 helpers in `@Vis/private/` used only inside `visual/`: plotting functions that turn a solver/sweep result into a figure, and a handful of data-prep/geometry/display-convention helpers those plots (and GUI callers) share. Plain static methods on one class rather than free top-level functions or an instantiable object — there is no per-plot state to hold, and grouping under `Vis.` keeps those 43 names out of the general MATLAB namespace while still reading as ordinary function calls.

## What's here

**Angular/velocity-surface plots:** `plotAngularMap`, `plotVelSurface`, `plotGroupVelSurface`, `plotYoungsSurface`, `plotRitzModeMap`, `plotClassificationDiagnostic`.
**In-plane bulk-property curves** (2D analogues of `plotVelSurface`/`plotYoungsSurface`: one in-plane rotation about the fixed surface normal, from a `Material` alone): `plotVelCurve`, `plotYoungsCurve`.
**Single-angle curve analogues** (for `CalcSingleHS`/`CalcSingleLayered`, no angle axis to sweep): `plotRitzModeCurve`, `plotGreenCurve`, `plotClassificationCurve` — 1D counterparts of the map functions above, same read-only-the-already-computed-data design, same argument shape minus the angle dimension.
**Green's-function/dispersion maps:** `plotGreenMap`, `plotDispersionMap`, `plotDispersionCurves`, `plotPolarHeatmap`.
**Ritz spectrum:** `plotRitzSpectrumMap`, `plotRitzSpectrumCurve` — the Ritz modal sum |S(v)| rebuilt from the stored modal numerators, the Ritz-side counterpart of the Green's-function map/curve; see "Ritz spectrum plots".
**Plate (Lamb) counterparts** (mode type/confidence in place of SAW recognition — `docs/reference/architecture/plate.md`): `plotRitzModeMapPlate`, `plotRitzModeCurvePlate`, `plotDispersionCurvesPlate`.
**Modal-shape (displacement field) plots:** `plotModalShape`, `plotGreenModalShape`, `plotGreenModalShapeLayered`; with `dirs = 'rgb'` each draws one polarisation-coloured panel per layer instead of one signed panel per direction (`calcPolarisationRgb` + the private `visRgbShapeStack`), with `plotPolarisationKey` as its colour key.
**Field-extraction/geometry helpers:** `calcDispField2D`, `calcGreenDispField2D`, `calcGreenDispField2DLayered`, `calcSubstrateCutoffDepth`, `extractPlanarCut`, `calcModalShapeRowHeights`, `pcolorCenteredGrid`.
**Shared display conventions** (public rather than `@Vis/private/` because GUI code outside `visual/` must match them): `scaleGreenData` (the log/linear `|G|` display scaling and its axis label; the caller always names the component, e.g. `'G_{13}^{eff}'`, `'G_{33}'` for the isoFreq results, `'S'` for the Ritz spectrum, so a label cannot fall back to a component the data is not), `greenComponentData` (the `|G|` data and label of one Green component of a result — stored for `G13_eff`, recomputed for any other), `plateModeTypeStyle` (Plate mode-type names and colours, plus the two parity classes' — `Asymm-class` teal, `Symm-class` crimson, the midpoints of their type colours — drawn dashed by `plotDispersionCurvesPlate` where only the parity is exact), `classificationScoreScale` (a classification method's `'high'` / `'low'` standards, read off the scoring classes, and the score range the marker size spans — shared with the viewers' classification bar), `ritzModeScores` (each Ritz mode's Ritz score, the `'ritzScore'` criterion — see "Ritz-mode criteria").

**Errors and warnings** carry three-part identifiers `Vis:<function>:<condition>` (e.g. `Vis:plotGreenMap:badScaleMode`, `Vis:greenComponentData:noGreenData` — a helper's error carries the helper's own name). The classification plots' `noGreenBackground` warning names the cause of the missing background per component: the calculation mode for a Green component, `calcSpotGreenMap`/`calcSpotGreen` for `'spot'`, the missing modal numerators for `'ritzSpectrum'`.

**Green component.** `plotGreenMap`/`plotGreenCurve` take `component` (default `'G13eff'`), resolved by `Vis.greenComponentData`: the ±k symmetrised `|G13_eff|` (`greenAbsG13EffMap`/`greenAbsG13Eff`, the only Green magnitude a Calc result stores; the ±k symmetrisation is in `green.md`), or any `'GIJ'` (one-sided `G_IJ(+k)`, `I` = force direction, `J` = displacement direction, e.g. `'G13'` = `G13_+`, `'G33'`) or `'GIJeff'` (±k symmetrised), which is recomputed for that call (`greenComponentMap` on a sweep, `greenComponent` on one angle: one Green solve per angle) and not stored. `G13_eff` is the default because it is the spectrum the Green existence scores read (`forwardCalcs_modeClassification.md`). Every component comes from the same axis and damping (η = 3e-3), so they compare like for like. Labels are `'G_{13}^{eff}'`, `'G_{13}^{+}'`, and, for the diagonal components, no superscript (`'G_{33}'`). `plotClassificationDiagnostic`/`plotClassificationCurve` take the same trailing `component` argument for their background (and, for the curve, the projection of the points), default `G13eff`, so the classified points sit on the spectrum they were decided on; `'ritzSpectrum'` draws the Ritz spectrum instead (the default on a `'ritzOnly'` result, which has no Green data), and `'spot'` (the stored `calcSpotGreenMap`/`calcSpotGreen` result, experimental) is accepted by `plotGreenMap`, `plotGreenCurve`, and both classification plots; `plotDispersionCurves`' Green background is `|G13_eff|` (`sweeps{iw}.greenAbsG13EffMap`). The Calc classes store the magnitude in single precision; `scaleGreenData` returns double, and `pcolorCenteredGrid` accepts either.
**Colormaps:** `ColMapGrayOrange`, `ColormapRWB`, `ColormapRYG`.
**Inverse-characterisation diagnostics** (experimental, `guliwerr/inverseCalcs/`): `plotSensitivitySpectrum`, `plotInversionFit`, `plotAssociationDiagnostic` — see "Inverse diagnostics" at the end of this document.

Every plotting function reads an already-computed solver/sweep result and never recomputes a parallel score or field — e.g. `plotClassificationDiagnostic`/`plotRitzModeMap` read `ModeClassification`'s `significantModesMap`/`diagnostics` fields directly rather than re-deriving a sensitivity metric in the graphics layer, and `plotGreenModalShape`/`plotModalShape` are built on `GreenSolver.calc`'s/`RitzSolver.calcDisplacement`'s own output rather than a duplicated partial-wave or basis-assembly loop. This is deliberate: a graphics-layer reimplementation of a score could silently drift from what the solver actually computed.

## Coordinate convention

Most plots operate in the project's standard fixed frame (x1 = propagation direction, x2 = remaining in-plane direction, x3 = surface normal/depth), reached via `Material.GetStandardDirMat`/`Material.CalcRotMat` exactly as `GreenSolver` does (see `docs/reference/architecture/green.md`). `plotVelSurface` and `plotGroupVelSurface` both take `mater.GetStandardElastTensor(0)` before sweeping — one fixed local frame, axis-labelled `x_1 (in-plane ref)` / `x_2 (in-plane)` / `x_3 (surface normal)`. `plotModalShape`/`plotGreenModalShape` use the same convention for their direction titles (`u_x` = propagation direction, `u_y` = in-plane, `u_z` = out-of-plane).

`extractPlanarCut` is convention-agnostic by design: it takes an arbitrary `planeNormal` and doesn't assume which axis is "surface normal," precisely because it needs to work on `plotVelSurface`'s and `plotGroupVelSurface`'s fixed-frame output alike (where a full-sphere sweep restricted up front would already give the right in-plane cut).

## Colormap conventions

Three GuliweRR colormaps, kept deliberately separate by data type, plus MATLAB's own `gray` where it fits:

| Colormap | Used by | Why |
|---|---|---|
| `ColormapRWB` | `plotModalShape`, `plotGreenModalShape`, `plotGreenModalShapeLayered` (fixed `clim([-1,1])`); `plotSensitivitySpectrum`'s signed transformation-matrix heat map | Displacement fields (and transformation-matrix entries) are signed; a diverging red-white-blue map with a true white zero is the physically apt choice for a quantity that crosses zero. |
| `ColMapGrayOrange` | `plotGreenMap`, `plotDispersionMap`'s heatmap cases, `plotDispersionCurves`' Green background, `plotRitzSpectrumMap` | `\|G\|` is a magnitude — sequential grayscale-through-orange, no meaningful zero to centre on. Matched to the Green-map figures of the UTGS paper (arXiv:2510.10696): grey for the lower ~62 % of the colour range, then orange to dark red, so with the colour limits set per map the continuum reads as grey structure and only the SAW/pSAW peaks turn red. |
| `ColormapRYG` | `plotAssociationDiagnostic`'s per-point value of the modal assurance criterion (MAC) (as the axes colormap standalone; as explicit per-point RGB in overlay mode, leaving a background's colormap untouched) | A quality score in [0,1] whose value itself means something (0 = bad, 1 = good): red-yellow-green traffic-light semantics, so red reads as "look at this". Not a perceptually uniform map like `parula`, whose brightest colour (yellow) at the high end would read as a warning for a score where high is good. |
| plain `gray` (unflipped) | `plotClassificationDiagnostic`/`plotClassificationCurve` (`colorBy='score'`/`'confidence'`; explicit per-point RGB over the points' own range with their own colour bar and a dark outline, leaving the background's colormap, limits, and colour bar untouched), `plotRitzModeMap` (with red shades below the veto level for `criterion='freqDisp'` on a half-space, see "Ritz-mode criteria"), `plotRitzModeMapPlate` (`criterion='confidence'`) | Low score → black, high score → white (MATLAB's built-in `gray` already maps low data to row 1/black, so this is `colormap(hAx, gray)` unflipped, not `flipud`). Chosen so low-score points fade into a `ColMapGrayOrange` background (used as an overlay in `plotClassificationDiagnostic`) rather than competing with it for a third hue. |

`plotClassificationDiagnostic`/`plotClassificationCurve` draw their per-type points in a fixed order — `limiting` (shown at `refLevel='full'` only), `pseudoRayleigh`, `Rayleigh`, `SAW` — rather than `unique()`'s alphabetical default. Alphabetical order puts `'limiting'` after `'SAW'` (`S` < `l` in ASCII), so a limiting-velocity reference point drawn at nearly the same map coordinate as a real SAW/Rayleigh mode could silently cover it; the fixed draw order keeps mode points on top of the limiting reference, and limiting points additionally use a smaller fixed marker so any remaining halo is less likely to obscure a nearby mode point. This complements `forwardCalcs_modeClassification.md`'s safeguards in `associateLimitingMode` (which prevent a genuinely spurious duplicate entry at a shared coordinate) by addressing the separate, purely visual risk that two *correct*, independently classified points occlude each other once drawn.

`plotGreenMap`/`plotDispersionMap`'s heatmap cases default to `scaleMode='log'`, plotting `log10(|G|/max|G|)` rather than plain `|G|` — a linear scale buries the sharp SAW peak against a much broader pseudo-SAW/background signal. `climRange` defaults differ between the two (`[-4,-1]` vs `[-5,-2]`) because they display different Green scans (isoWavevec angular map vs. isoFreq dispersion map), with no reason to assume one numeric range suits both. The isoWavevec maps are at η = 3e-3 (`SawSpectrum.ETA`, the damping of the existence solve, `green.md`): every pole is broadened to a finite, sampling-independent height, so off-peak features sit only a few decades below the normalising peak. `plotGreenMap`, `plotDispersionCurves`, and `plotRitzSpectrumMap` default to `[-4,-1]`; `plotDispersionMap`'s `[-5,-2]` (isoFreq, default η) is tuned separately. For its 1D `CalcIsofreqSingleLayered` line `climRange` is the y-range instead, default `[-5,0]`: the normalised peak sits at 0, so the heatmap default would cut it off. The isoWavevec axis starts at 0.3 km/s (the Calc classes' Green axis, `forwardCalcs.md`), so the lowest part of a Green map or curve is normally empty.

## Classification plots: marker size by score, weak and strong entries

> **Experimental.** Surface-wave classification is checked against the measured maps published in Grabec et al. 2024 and the UTGS paper (arXiv:2510.10696), and there is no general agreement on which spectral peaks count as surface waves in strongly anisotropic materials. Thresholds, scores and the interface may change.

`plotClassificationDiagnostic`/`plotClassificationCurve` take `refLevel` (default `'full'`), which sets how much of the classification is drawn, in three cumulative tiers. Points of type `'other'` (unclassified or rejected candidates) are never drawn at any tier — these plots read out the classification, they are not a catalogue of every candidate considered.

- `'sawOnly'` — the surface-wave family only (`SAW`, `Rayleigh`, `pseudoRayleigh`), no reference line.
- `'sawLimit'` — the same points plus one Christoffel reference line chosen by family: the longitudinal limiting velocity for a half-space, the substrate shear limiting velocity for a layered stack (the bound above which the wave leaks into the substrate).
- `'full'` — in addition the `'limiting'` points, the Ritz modes sitting at a bulk-wave limiting velocity (for a layered stack this is what shows the substrate-shear boundary as discrete data).

One private helper (`visClassificationTypesAllowed`) holds this rule for both functions, so they show the same modes at the same tier.

`plotClassificationDiagnostic`/`plotClassificationCurve` (and the viewers' classification overlay, which restyles their handles — `gui_viewers.md`) show each entry's existence score and grade (`forwardCalcs_modeClassification.md`, "Standards and grades") as well as its type:

- **Size by score.** The marker area is linear in the entry's `score` (a log10 amplitude ratio, so linear in dB) over `Vis.classificationScoreScale(method, isLayered).sizeRange`, clipped at both ends. The range starts at the method's `'high'` threshold, where the weakest accepted entry sits, and ends one decade (20 dB) above its `'low'` threshold where both standards are on the score scale, or 1.5 decades (30 dB) above `'high'` where `'low'` is compared with a separate structure-relative score (half-space `'green'` and `'refined'`). The strong entries of a typical map then spread over the size range instead of saturating it. The scale is per method: sizes compare entries of one classification, never across methods. Entries without a score get a fixed size, `'limiting'` entries a smaller fixed one.
- **Weak entries open.** An entry graded `'weak'` (accepted at the active, looser standard but not at the method's `'low'`) is drawn as an open marker with `colorBy='type'`, and with a transparent face with `colorBy='score'`/`'confidence'`; `'strong'` entries are filled. Each scatter handle carries `UserData.isWeak`, so a caller restyling the points (the GUI overlay draws every point as a ring) can keep weak entries apart — the overlay draws them as faint rings.
- **`colorBy`.** `'type'` (default: one scatter series per type, legend), `'score'` (the entry's `scoreDb`, on its method's scale) or `'confidence'` (`|modeVel − greenPeakVel|`, the distance of the bound Ritz mode from the Green peak it was matched to, so 0 is a perfect match; NaN where no Green match was made).

The scales and standards come from the scoring classes' own constants (`classificationScoreScale` reads them, never copies them), so a recalibration changes the plots and the classification bar together.

## Ritz spectrum plots

`plotRitzSpectrumCurve`/`plotRitzSpectrumMap` draw the Ritz spectrum — the modal sum the `'ritz'` classification scores (`forwardCalcs_modeClassification.md`, "The modal sum (the Ritz spectrum)") — as the Ritz-side counterpart of the `|G13_eff|` map or curve. They follow the read-only rule above: `RitzScore.spectrum` rebuilds |S|
from the per-mode numerators every result stores (`ritzScoreNum`, taken before eigenvector
pruning) and the Ritz velocities, with no solve, on both calculation modes. A result without
stored numerators errors (`Vis:plotRitzSpectrumCurve:noRitzSpectrum`). On a `'ritzOnly'` result, which
has no Green data, the Ritz spectrum is the only response background, and the classification
plots default to it there. One private helper (`visRitzSpectrumData`) evaluates |S| for the curve,
the map and the classification curve's projection, and one (`visHasRitzSpectrum`) decides whether a
result (every angle of a sweep) has it.

- **Curve.** On the result's own Ritz score axis (`ritzScoreVelAxis`, `RitzScore.VEL_STEP` = 2 m/s).
  `showCands` (default `false`, as on the map; the curve viewer turns it on) marks the Ritz
  candidates: down-triangles at the modal-sum peaks, circles at their supporting modes
  (`RitzScore.localMode`). The third output `spec` (`velAxis`, `absS`, `cands`) lets a caller
  reuse the drawn spectrum.
- **Map.** `plotRitzSpectrumMap(sweepResult, scaleMode, climRange, plotType, hAx, showCands)` —
  the argument order of `plotGreenMap`, so `hAx` is 5th in both (`plotType` is `'cartesian'`, the
  only value). Every angle evaluated on one common axis (the union of the angles' Ritz score axes,
  at `RitzScore.VEL_STEP`) and normalised to the map's maximum; `climRange` defaults to `[-4,-1]`
  as for `plotGreenMap`. `showCands` (default `false`) marks each angle's candidates at their
  supporting modes' velocities.

Both use `Vis.scaleGreenData` with the component label `'S'` — the same log10 normalisation to the
plot's own peak as `plotGreenCurve`/`plotGreenMap`, for direct comparison, with the axis labelled
as the Ritz spectrum rather than as a Green component.

## Ritz-mode criteria

`plotRitzModeMap`/`plotRitzModeCurve` draw every computed Ritz mode (not only the classified ones),
shaded (map) or placed (curve) by `criterion`, default `'ritzScore'` (the viewers' default too).
The per-mode values and the list of criterion names come from one private helper
(`visRitzCriterion`), so a criterion means the same number on the map and the curve:

| `criterion` | Value per mode | Display |
|---|---|---|
| `'ritzScore'` | the Ritz score (dB) of the Ritz candidate the mode supports (`Vis.ritzModeScores`: the candidate whose supporting mode, `RitzScore.localMode`, is this mode; the highest if it supports several; `RitzScore.candidateScore`: half-space `dScore`, layered `dScore + polTerm` — the value the `'ritz'` rule thresholds, from the same function the rule uses). Every scored candidate counts, accepted or not, so the view shows where the rule looked, not only what it kept | scored modes on the `gray` scale; modes supporting no candidate drawn faint (map: a second scatter handle; curve: the scored modes joined by a line with small markers, the others as faint grey dots on a baseline below them) |
| `'freqDisp'` | `ritz.diagnostics.freqDisp`, the half-space non-dispersion veto quantity | half-space: the veto level `RitzScore.MIN_FREQDISP` (0.3) marked — on the map the colour limits are fixed to [0, 1] and values below the level are shaded dark-to-light red, with a "veto" tick on the colour bar; on the curve a dashed red line. Layered: no veto is marked, since the layered rule does not use `freqDisp` (the film makes true guided modes dispersive) |
| `'depthInsensitivity'` | `ritz.diagnostics.depthInsensitivity`: how little the mode's velocity changes with the Ritz domain depth (large for surface modes) | `gray` scale; a depth-profile diagnostic |

`freqDisp` and `depthInsensitivity` are read straight off `ritz.diagnostics`, never recomputed. The
upper velocity cutoff (`velCutoffFactor` × the longitudinal limiting velocity) uses the sweep's
limiting-velocity map, or each angle's own limiting velocity on a `'ritzOnly'` sweep, which
assembles no map.

## Data-prep helpers

`calcDispField2D`/`calcGreenDispField2D`/`calcGreenDispField2DLayered` assemble the signed 2D (depth × lateral) displacement field their plotting counterparts render, kept as separate functions rather than inlined so the field itself is independently testable and reusable (e.g. by a GUI computing a decay-based cutoff before deciding whether to plot at all). All three build the field as `real(depthProfile * lateralFactor)` where `lateralFactor = exp(i*pi*(x+1))` is kept genuinely complex through the multiplication — simplifying to a real cosine factor up front would silently drop the depth profile's imaginary part, since the underlying eigenproblem uses a Hermitian (conjugate-transpose) inner product and is complex in general, not real symmetric. The real part is a snapshot at one instant; which instant depends on the mode's phase, which `RitzSolver.calcDisplacement` fixes (largest in-plane coefficient real positive) so the picture does not depend on the eigensolver's arbitrary choice. `calcDispField2D` normalises by the single global max *positive* value across every direction/layer, not `max(abs(...))` — a negative-dominant mode can therefore normalise to values outside `[-1,1]`, which the fixed `clim([-1,1])` in the plotting functions will visibly clip.

`calcGreenDispField2DLayered` is the layered counterpart of `calcGreenDispField2D`, built on `GreenSolver.calc`'s `k3OutLayered`/`polarizationULayered`/`partialAmplitudeLayered`/`hScaleOut` (populated when `nargout>1` and `structure.nLay>1` — see `docs/reference/architecture/green.md`, "Depth-resolved field, layered structures") rather than the half-space-only `.dispField`. Each film is reconstructed over its own finite `relDepth`, mapped to `RitzSolver`'s `ti∈[-1,1]` convention; the substrate, semi-infinite to `GreenSolver`, reuses `structure.calcParams(1).relDepth` purely as a display extent, as if it were another film of that thickness. At matching `meshSpacing`, Ritz and Green then sample an identical `ti` grid per layer, index for index, allowing a direct shape comparison. Like `calcDispField2D`, it returns the full, uncropped field; cropping happens in `plotGreenModalShapeLayered` (below).

`calcSubstrateCutoffDepth`/`calcModalShapeRowHeights` are pure axis-layout helpers for `plotModalShape` and `plotGreenModalShapeLayered` — they decide how much vertical figure space each layer gets, independent of what is drawn into it. `calcSubstrateCutoffDepth` implements two selectable substrate-display modes (`'decay'`: truncate where the mode's own computed displacement magnitude drops below a threshold fraction of its interface value; `'fixedMultiple'`: truncate at a fixed multiple of the film-stack thickness) plus `'none'` (no truncation, true-scale). `calcModalShapeRowHeights` is a non-cropping alternative (`plotGreenModalShapeLayered`'s `substrateCutoff='boosted'`, and the viewers' axes grid): every layer gets a guaranteed minimum height fraction before the remainder is split proportionally to true `relDepth`, so a thin film next to a much deeper substrate stays visible without discarding any substrate data — a plain-proportional split can compress a thin film to ~1% of the figure height, which reads as invisible.

`plotGreenModalShapeLayered` reuses `plotModalShape`'s axis-stacking block (`layBottom`/`layHeightFrac`, the substrate-cutoff crop, top-row-only titling) rather than `plotGreenModalShape`'s single-layer case, since the problem is the same one `plotModalShape` solves: several layers of different `relDepth` sharing one figure. It defaults `substrateCutoff` to `'decay'`, not `plotModalShape`'s `'none'`: the substrate extent is a display-only reuse of `relDepth(1)` (see above), not a physically meaningful true scale like a Ritz substrate truncation, so showing it in full would usually give a mostly empty panel.

`pcolorCenteredGrid` (shared by `plotDispersionMap`, `plotGreenMap`, and `plotPolarHeatmap`) fixes a `pcolor` gotcha documented in `docs/pitfalls.md`: plain `pcolor(x,y,C)` draws cell `(i,j)` spanning `(x_i,y_j)` to `(x_i+1,y_j+1)`, so every sample sits at a cell's lower-left corner rather than its centre, offsetting the whole map from its own axis ticks. The helper computes edge grids that centre each cell on its sample value, and accepts decreasing or degenerate axes — needed because `CalcIsofreqAngSweepLayered`'s `kParRange = omega0 ./ vAxis` decreases when `vAxis` increases, and repeated equal radius samples are a real input in the polar case. For the polar case specifically, radius edges are clamped to `>=0` so an extrapolated inner edge can't flip to the opposite angle under `pol2cart`.

`extractPlanarCut` is a generic (surface-agnostic) helper: given a `(theta,phi)`-parametrised 3D surface (as produced by `plotVelSurface`/`plotGroupVelSurface`), it finds the zero-crossing contour of a cutting-plane's signed-distance function over the parameter grid and projects it into 2D in-plane coordinates. It needs the full-sphere sweep to already exist rather than restricting the sweep to one plane from the start, because for a vector-valued surface (group velocity) the plotted point is *not* simply the wave-normal direction scaled by a scalar — group velocity can point off-plane even for an in-plane wave normal — so an in-plane restriction at sweep time would silently miss real crossings. For the simpler scalar case (phase velocity/slowness) the two approaches happen to agree exactly, a useful correctness check.

## Polarisation-RGB modal-shape view

`dirs = 'rgb'` on `plotModalShape`/`plotGreenModalShape`/`plotGreenModalShapeLayered` draws the displacement field in one polarisation-coloured panel per layer. At each point the hue is the unit vector p = (|u1|, |u2|, |u3|)/|u| weighting one base colour per direction, hue = p1·red + p2·blue + p3·green (the private `visPolarisationColours`, shared by the panels and the key) — red = propagation, blue = in-plane transverse, green = out-of-plane — and the brightness is |u| / max|u|, blended from white (`pixel = 1 − a + a·hue`), so zero motion is white like `ColormapRWB`'s zero. Green is darkened to 0.65: pure (0,1,0) has about 3.4× the luminance of red and 10× that of blue, so pale green regions vanished into the white background and u3 read differently from u1/u2 at equal amplitude. Using the unit vector rather than the per-channel maxima keeps the hue a pure *direction*: every direction is one point of the sphere's positive octant, which is exactly what `plotPolarisationKey` draws. One normaliser (max of |u|, not the signed panels' positive-only maximum) covers all layers, so nothing clips and a weak layer stays visibly weak. It is a snapshot at one phase, like the signed panels: u1 and u3 of a Rayleigh wave are 90° out of phase and appear as separate stripes. It hooks in through the existing `dirs` argument — the cropping and row-height logic of the three plot functions is reused unchanged, and only their final panel loop is swapped. With `hAxCellIn` the caller supplies a `{1 x nLay}` cell and draws the key itself (the GUIs build a hidden RGB axes set plus a key axes once, in `GuiCommon.shapeAxesGrid`, and switch sets with `GuiCommon.setShapeDisplayMode`).

## retentionLevel and modal-shape plots

`plotModalShape` requires `ritzSolver.eigVecs_con` to already have enough columns for the requested mode — it errors clearly (`Vis:plotModalShape:modeNotAvailable`) rather than silently doing the wrong thing if not. This ties directly to `RitzSolver`'s `retentionLevel` setting (`'full'` keeps eigenvectors; other levels prune them to save memory across an angular sweep) — a caller building a sweep with a pruned `retentionLevel` and later wanting a modal-shape plot for one specific angle/mode needs to reconstruct/recompute that single `RitzSolver` with `retentionLevel='full'` first. `Vis` does not do this recompute itself; it is a caller-side responsibility, documented at the point of use rather than re-explained here — see the Ritz solver's own retention-level handling for the mechanism.

## Duck-typing across HS/Layered result classes

Several functions read fields that are named identically across `CalcAngSweepHS`/`CalcSingleHS` and their `*Layered` counterparts (`.angles`, `.greenVelAxis`, `.greenAbsG13EffMap`/`.greenAbsG13Eff`, `.significantModesMap`) and dispatch by `isa()`/`isprop()` rather than by a shared base-class contract where the naming actually differs. `plotRitzModeMap` checks `longVelMap` vs. `subLongVelMap` (HS's system-wide longitudinal limiting velocity vs. Layered's substrate-only one); the classification and Ritz-mode plots decide HS vs. layered by class through one private helper (`visIsLayered`) and `shearLimVels` vs. `subShearLimVels` on the per-angle `cs{iAngle}` object — these two names genuinely differ, not just aliases of the same field. `plotDispersionMap` instead dispatches on four structurally different result classes (`CalcWavevecAngSweep2Layered`, `CalcFreqAngSweep2Layered`, `CalcIsofreqAngSweepLayered`, `CalcIsofreqSingleLayered`) via `isa()`, since those genuinely hold different-shaped data (2D scatter of classified points vs. Green-magnitude heatmap vs. 1D spectrum), not just differently-named fields on one shape.

## Polar heatmaps: why `plotPolarHeatmap` exists

MATLAB has no polar equivalent of `pcolor` (`polaraxes()` offers `polarplot`, `polarscatter`, and the like, but no polar colour-map plot), so a true 2D angle×radius colour map on polar axes isn't directly available. `plotPolarHeatmap` works around this by converting the `(angle,radius)` grid to Cartesian `(x,y)` via `pol2cart`, `pcolor`-ing that on an ordinary `axes()`, and hand-drawing radial rings/angular spokes as a substitute for the ticks/labels a real `polaraxes()` would give for free. It is generic (not Green-specific) and is shared by `plotGreenMap`'s and `plotDispersionMap`'s `plotType='polar'` option — colour scaling (log/linear, colormap, clim, colorbar) stays the caller's responsibility so both display modes share identical colour treatment. `plotAngularMap`'s own `'polar'` mode is unrelated and simpler: it's a scalar `polarplot` scatter (angle, 1/velocity), which polar axes handle natively, so it uses real `polaraxes()` directly rather than this workaround.

## Inverse diagnostics

> **Experimental.** The inverse module is validated on synthetic data only; the interface may change. Its pseudo-surface-wave tracking is new.

Three plots serve `guliwerr/inverseCalcs/`. Like the others they only read objects that already exist and recompute nothing.

- **`plotSensitivitySpectrum(sensitivityAnalysis, hFig)`** reads a computed `SensitivityAnalysis` (`normalisedSensitivityRoots`, `transformMatrix`, `sensitivityCutoff`, `nOptimisedConstants`). Left axes: a log-scale bar chart of the normalised square roots of the sensitivity eigenvalues, i.e. how strongly the error is amplified for each combination of elastic constants relative to the best-determined one; bars below `sensitivityCutoff` (the combinations the inversion freezes) are grey, and the cutoff is a dashed line. Right axes: the *signed* transformation matrix as a heat map (rows are the independent Voigt constants, columns the combinations), on `ColormapRWB` symmetric about zero — the sign tells, for cubic symmetry for example, a longitudinal-like `c11+c12` combination from a shear-like `c11−c12` one. Outputs: `[hBar, hAx, hHeat]`, with `hAx` the two axes.
- **`plotInversionFit(measured, associationFinal, associationInitial, hAx)`** reads the full `MeasuredVelocities` dataset and a `ModeAssociation` (the recovered one, normally `inversion.association` after `calc()`), plus optionally an earlier `ModeAssociation` snapshot as the initial guess (`ModeAssociation` is a value class, so the variable the inversion was built from is untouched by `calc()`). On one propagation-angle × velocity axes it draws the measured points (black), the initial-guess velocities (orange, if given), the recovered velocities (red, filled), and the measured points that found no matching mode within the velocity tolerance (grey crosses). The marker shape marks the binding class of the point: bound to a Ritz mode, to a limiting velocity, or to a pseudo-surface wave. A point counts as associated if the final association holds a point at the same angle with the same measured velocity.
- **`plotAssociationDiagnostic(association, hAx, overlayMode)`** reads a `ModeAssociation` after at least one rebind. It draws each point's propagation angle against its calculated velocity, coloured by the MAC value achieved when the point was bound to its Ritz mode (`ColormapRYG`, red = poor); points flagged `modeCollision` get a red ring. A collapsing MAC is the visible signature of a binding going wrong. Points bound to a limiting velocity are routed through Christoffel, have no MAC, and are drawn as a separate grey series. With `overlayMode = true` only markers are drawn, coloured by explicit RGB so that the axes' colormap is untouched, for overlaying on a `Vis.plotGreenMap` background.
